# Source Consolidation for Multi-Action Mom Families

## Status

This document frames an open source-layout discussion. It is not an approved design, mandatory follow-up, roadmap commitment, implementation priority, deployment prerequisite, or audit requirement. It does not move Solidity sources, alter contract behavior, change artifact identifiers, or modify deployment records.

Within this document, normative language describes constraints that would apply if the candidate consolidation were adopted. It does not require consolidation to happen.

## Candidate Direction

One candidate direction is to consolidate sources only when one Mom exposes several emergency actions that are currently represented by separate spell source files. Under that approach, single-target and registry-global spells would remain separate.

`Global*` spells have a different subject model from their single-target counterparts. They select subjects through an authoritative registry, expose range execution, and have different failure and operational characteristics. Those differences justify separate production and test files even when both spells ultimately call the same Mom.

Under the current V2 implementation, stUSDS is the only family that clearly meets the multi-action consolidation criterion:

- `StUsdsRateSetterDissBudSpellV2`;
- `StUsdsRateSetterHaltSpellV2`;
- `StUsdsWipeParamSpellV2`.

Clip breaker, line wipe, and OSM stop do not meet this criterion. Their paired files represent single-target and registry-global subject models rather than multiple actions on one subject.

## Motivation

The three stUSDS spells are separate typed actions against the same Mom family. Their production sources repeat closely related interfaces, while their unit and integration tests repeat family setup. Keeping the deployed contract types distinct remains valuable, while colocating the family can reduce navigation and duplicated setup.

The useful consolidation boundary is therefore the Solidity source file, not the deployed contract type. Each emergency action should retain a typed constructor and a bytecode-constrained Mom call.

Combining the actions into one generic deployed contract would require an enum-driven superset constructor, generic parameter slots, or arbitrary calldata. Dynamic constructor calldata would normally be stored in contract storage. During batch `delegatecall`, the leaf would then read the batch contract's storage rather than the leaf's storage, making the execution path incorrect. Custom runtime-code data encoding could avoid storage, but it would require assembly-heavy generated bytecode and another deployment abstraction. That complexity is not justified by the reduction in contract variants.

## Candidate Goals

If adopted, the consolidation would:

- consolidate the three stUSDS production sources into one family source;
- consolidate their unit tests into one colocated unit-test source;
- consolidate their integration tests into one colocated integration-test source;
- retain separate typed spell contracts for each action;
- retain precise constructor parameters and public immutable getters;
- keep each permitted Mom action constrained by the deployed spell bytecode;
- consolidate duplicate stUSDS interfaces within the family source;
- keep mocks inline in the consolidated tests;
- update every import and artifact identifier affected by the stUSDS source moves;
- preserve the existing stUSDS deployment-script contracts and entrypoints.

## Candidate Non-Goals

The candidate consolidation would not:

- combine any single-target spell with its `Global*` counterpart;
- move or rename clip-breaker, line-wipe, or OSM-stop sources;
- merge distinct stUSDS spell contracts into an enum-driven family contract;
- accept arbitrary constructor calldata;
- introduce a generic low-level Mom executor;
- use generic `bytes32` argument slots or manually decoded parameter unions;
- append parameter data to custom runtime bytecode;
- add a uniform `params()` or `callData()` metadata interface;
- add shared mock files or a new test inheritance hierarchy;
- implement the separate `done()` simplification, change batch eligibility, or alter operational publication rules.

Existing typed immutable getters and deployment-manifest fields remain the machine-readable parameter surface for off-chain tooling.

## Candidate stUSDS Layout

Replace:

```text
src/stusds/
├── StUsdsRateSetterDissBudSpellV2.sol
├── StUsdsRateSetterDissBudSpellV2.t.sol
├── StUsdsRateSetterDissBudSpellV2Integration.t.sol
├── StUsdsRateSetterHaltSpellV2.sol
├── StUsdsRateSetterHaltSpellV2.t.sol
├── StUsdsRateSetterHaltSpellV2Integration.t.sol
├── StUsdsWipeParamSpellV2.sol
├── StUsdsWipeParamSpellV2.t.sol
└── StUsdsWipeParamSpellV2Integration.t.sol
```

With:

```text
src/stusds/
├── StUsdsSpellsV2.sol
├── StUsdsSpellsV2.t.sol
└── StUsdsSpellsV2Integration.t.sol
```

This proposed layout organizes the current nine stUSDS files into three family-level files without reducing the number of typed spell contracts.

Deployment scripts are already grouped by subject and should not be renamed or merged as part of this work.

## Candidate Production Source Design

`StUsdsSpellsV2.sol` should continue exposing:

- `Param`;
- `StUsdsRateSetterDissBudSpellV2`;
- `StUsdsRateSetterHaltSpellV2`;
- `StUsdsWipeParamSpellV2`.

It should contain one family-local `StUsdsMomLike` interface with:

- `stusds`;
- `dissRateSetterBud`;
- `haltRateSetter`;
- `zeroCap`;
- `zeroLine`.

After the `done()` simplification described in [`mom-and-integration-testing.md`](./mom-and-integration-testing.md), it should contain one family-local `StUsdsRateSetterLike` interface with:

- `stusds`;

Do not consolidate `StUsdsLike`, `VatLike`, or rate-setter read methods that the prior implementation used only for concrete `done()` overrides. Subject metadata and constructor object-graph checks required after the simplification should remain family-local.

Use this source order:

1. `Param`;
2. family-local interfaces;
3. `StUsdsRateSetterDissBudSpellV2`;
4. `StUsdsRateSetterHaltSpellV2`;
5. `StUsdsWipeParamSpellV2`.

Do not introduce an abstract stUSDS base solely to deduplicate constructor assignments or object-graph checks. Small action-specific duplication is preferable to an inheritance layer that obscures each deployed spell's behavior.

## Public Interface Preservation

Source consolidation itself should preserve the following interfaces and behavior as they exist after the preceding `done()` simplification:

- contract name;
- constructor types and argument order;
- public constant and immutable getter names and types;
- `Param` member names, order, and values;
- `description()` output;
- the inherited always-false `done()` ABI behavior;
- `schedule()` behavior;
- emitted event signatures and indexed fields;
- revert behavior and prefixed messages;
- batch eligibility and storage discipline.

The stUSDS deployment-script contract names and every existing `run()` overload must also remain unchanged. Only Solidity import paths should change.

## Artifact and Bytecode Impact

Moving and combining the Solidity sources changes artifact identifiers:

```text
src/stusds/StUsdsRateSetterHaltSpellV2.sol:StUsdsRateSetterHaltSpellV2
src/stusds/StUsdsSpellsV2.sol:StUsdsRateSetterHaltSpellV2
```

The same applies to the other two stUSDS contracts.

Solidity metadata includes source paths and source hashes. Runtime and creation bytecode may therefore change even when the executable logic and ABI remain equivalent. The implementation must not use bytecode equality as its compatibility assertion.

Before implementation:

1. re-read `deployments/1/v2.json`;
2. identify only records whose `contractName` or artifact path references one of the three old stUSDS sources, `StUsdsSpellsV2.sol`, or the three affected stUSDS contract names;
3. allow unrelated V2 records to remain and preserve each unrelated record and its `sourceCommit` unchanged;
4. proceed without a deployment-record migration only if no affected record exists;
5. stop and define an explicit source-path, codehash, and deployment-record migration if any affected record exists.

The production V2 manifest had no records when this document was written, but that historical state is not a global emptiness requirement. The implementation gate concerns only affected stUSDS records.

## Potential Consumer Updates

### Solidity imports

Update stUSDS imports in:

- `script/stusds/DeployStUsdsV2.s.sol`;
- its colocated unit and integration tests;
- batch integration tests that construct stUSDS leaves;
- the consolidated stUSDS unit and integration tests.

Use named imports from `StUsdsSpellsV2.sol`. Do not add forwarding source files at the old paths because they would create two canonical artifact locations and preserve the file-count problem.

### CLI, fixtures, and documentation

Search the repository for all three removed stUSDS source paths and update any artifact identifiers in:

- CLI documentation examples;
- deployment-draft tests;
- manifest-validator tests;
- migration-validator tests;
- valid and invalid V2 manifest fixtures;
- repository documentation.

Keep each `contractName` unchanged. The V2 schema requires an artifact path and contract pair but does not require one contract per source file.

Do not change clip-breaker, line-wipe, OSM-stop, or `Global*` artifact identifiers as part of this work.

## Candidate Test-File Organization

`StUsdsSpellsV2.t.sol` should retain separate test contracts:

```text
StUsdsRateSetterDissBudSpellV2Test
StUsdsRateSetterHaltSpellV2Test
StUsdsWipeParamSpellV2Test
```

Mocks should remain inline. A mock may be shared within the file only when the tests require the same behavior and state model. Do not create a separate stUSDS mock source or a new shared test base solely because the tests now share a file.

`StUsdsSpellsV2Integration.t.sol` should likewise retain separate integration-test contracts. This preserves `--match-contract` isolation for each action while reducing navigation overhead.

If both proposals are adopted, the `done()` and dependency simplification in [`mom-and-integration-testing.md`](./mom-and-integration-testing.md) would be implemented before source consolidation so obsolete `done()`-only stUSDS interfaces and lookups are not moved into the consolidated file. The RPC and action-wiring tests from that proposal would then be added directly to the final stUSDS test files.

## Possible Implementation Sequence

### Phase 1: Apply the candidate `done()` simplification first

- implement and verify the always-false base `done()` design in [`mom-and-integration-testing.md`](./mom-and-integration-testing.md);
- remove the obsolete stUSDS `done()` overrides and dependencies before defining the consolidated interface set;
- update normalized ABI output, bindings, and fixtures for the intentional `done()` JSON ABI `stateMutability` change from `view` to `pure`;
- capture the resulting post-simplification ABIs, constructors, retained immutable getters, and execution behavior as the consolidation baseline without claiming byte-for-byte compatibility with the pre-simplification ABI.

### Phase 2: Capture consolidation compatibility evidence

- confirm that `deployments/1/v2.json` contains no affected stUSDS records;
- inventory unrelated V2 records and their `sourceCommit` values so the consolidation can prove they remain unchanged;
- record the current stUSDS file inventory;
- capture normalized ABI output for the three stUSDS spell contracts;
- record their constructor signatures and the deployment script's `run()` signatures;
- run the existing non-integration suite as a baseline.

### Phase 3: Consolidate production sources

- create `src/stusds/StUsdsSpellsV2.sol`;
- consolidate the family-local interfaces;
- copy the three typed contracts without changing behavior;
- compile the new source before deleting any old source;
- compare normalized ABIs with the captured baseline.

### Phase 4: Consolidate unit tests

- create `src/stusds/StUsdsSpellsV2.t.sol`;
- preserve the three independent test-contract boundaries;
- inline only the mocks needed by those tests;
- run every action and parameter variant;
- remove the three superseded unit-test sources after the consolidated tests pass.

### Phase 5: Consolidate integration tests

- create `src/stusds/StUsdsSpellsV2Integration.t.sol`;
- preserve the three independent integration-test contracts;
- retain the existing RPC state setup and assertions;
- run each integration contract independently;
- remove the three superseded integration-test sources after the consolidated tests pass.

### Phase 6: Update consumers

- update `script/stusds/DeployStUsdsV2.s.sol` and its tests to import the consolidated source;
- update any batch integration importing stUSDS leaves;
- update every CLI fixture, manifest fixture, or document containing an old stUSDS artifact path;
- search the repository for every removed stUSDS source path.

### Phase 7: Remove superseded production sources

- remove the three old stUSDS production sources only after all imports have moved;
- verify that no old stUSDS artifact path remains;
- verify that no non-stUSDS source or test file was renamed or consolidated.

### Phase 8: Verify compatibility

- compare normalized pre-consolidation and post-consolidation ABIs;
- compare constructor and deployment-script signatures;
- verify unrelated V2 deployment records and their `sourceCommit` values are unchanged;
- run the complete repository validation;
- review bytecode differences as expected metadata and source-layout changes rather than requiring equality;
- inspect the final diff for changes outside the stUSDS family and its direct consumers.

## Possible Test Plan

### Solidity checks

```sh
forge fmt --check
forge build --sizes
forge test --no-match-path '**/*Integration.t.sol'
```

Also run:

- the stUSDS deployment-script unit tests;
- batch integration tests that use stUSDS leaves;
- each test contract in `StUsdsSpellsV2Integration.t.sol` against an appropriate RPC.

For a complete integration run:

```sh
ETH_RPC_URL=<mainnet-rpc> forge test --match-path '**/*Integration.t.sol'
```

### CLI and documentation checks

```sh
python3 -m compileall -q cli
python3 -m unittest discover -s cli/emergency_spells -t . -v
prettier --check --prose-wrap never README.md docs TODO cli/README.md
git diff --check
```

### Compatibility checks

For each of the three stUSDS contracts:

- normalize and compare `forge inspect <artifact> abi` before and after;
- verify constructor argument types and order;
- verify public immutable and constant getters;
- verify event topics and indexed fields;
- verify the deployment script still instantiates the same contract with the same parameters;
- verify batch integrations still execute leaf logic through the batch address.

## Possible Acceptance Criteria

If the candidate consolidation is adopted, the resulting implementation could be considered complete when:

- the stUSDS family contains exactly one production source, one unit-test source, and one integration-test source;
- all three typed stUSDS spell contracts remain available under their original names;
- source consolidation does not change constructors, getters, `Param`, events, descriptions, revert behavior, inherited always-false `done()` behavior, or execution semantics from the post-simplification baseline;
- normalized pre-consolidation and post-consolidation ABIs match;
- stUSDS deployment-script contracts and `run()` overloads remain unchanged;
- no generic execution, parameter union, or metadata encoding interface is introduced;
- no removed stUSDS source path remains in active imports, documentation, fixtures, or tests;
- clip-breaker, line-wipe, OSM-stop, and all `Global*` source boundaries remain unchanged;
- relevant unit, deployment, batch, integration, manifest, migration, and CLI tests pass;
- no affected stUSDS deployment record is silently invalidated;
- unrelated V2 deployment records and their `sourceCommit` values remain unchanged and do not block consolidation;
- the implementation remains compatible with the testing improvements described in `mom-and-integration-testing.md`.
